## Assessment

**The implemented v2 scope has substantial local verification, but I would hold the public release tag until the remaining release gates below are closed.** Two actual release blockers were discovered and fixed during this audit: the clean production web image failed to compile, and automatic pull-request preview cleanup failed against PostgreSQL. Both affected paths passed after correction.

The largest functional gap against both competitors is **backup and restore of application volumes**. Towbar's managed volumes preserve files across deployments; neither database-resource backups nor control-plane backups protect those files. This needs either implementation or an explicit operator backup procedure before describing persistent applications as fully protected.

Towbar's strongest current areas are manifest-driven environments, explicit permission boundaries across API/MCP and queued operations, built-in audit history, and log forwarding with bounded queues and persistent failure handling. Competitors have broader deployment inputs, service catalogs, scaling options, and enterprise identity integrations. Matching every competitor feature is not a prerequisite for a focused v2 release.

## Evidence and limitations

- Forced local gates were run rather than accepting Turbo cache hits.
- Eight fresh PostgreSQL test databases were migrated from the reset `001` schema. Docker, a disposable Temporal server, OpenSSH targets, storage emulators, and real provider protocol receivers were used where supported.
- Real Docker containers and SSH commands prove local runtime behavior. Simulated GitHub responses, local SMTP, storage emulators, and fixture pages do **not** prove real external accounts, internet TLS issuance, cloud IAM, email deliverability, or production infrastructure.
- Current official Coolify and Dokploy documentation was reviewed. Neither competitor was deployed or benchmarked in this audit. “Not verified” means the reviewed documentation did not establish support; it does not establish absence.
- Browser review sampled real fixture routes, desktop and a 390 px mobile audit-log view. It is not exhaustive browser, accessibility, or every-state visual certification.
- Local detailed logs and machine-readable run results are in `/tmp/towbar-v2-final-20260917/`. They are local audit evidence, not permanent CI artifacts. Historical screenshot evidence is kept separate from this run.

## UI/UX observations

Current sampled pages: Team Settings General/Members/Backup/Restore/API Keys/Audit Logs; personal profile, email/password, 2FA and API keys; repositories/apps/resources/servers; server Overview, Preparation and Terminal.

Confirmed observations include General before Members, separate members/invitation tables, a compact Add User form without confirm-password, first-sign-in password guidance, provider-not-configured backup/restore states, separate personal/team key ownership, authenticator and passkey sections, and server sidebar status/count indicators. Audit log columns are Event → Target → User → Time; event search filters its menu correctly, icons and avatars render, and the mobile filters precede search. Dense tables scroll horizontally on narrow screens. These checks do not establish pixel consistency in every table.

The development console reports React Aria `PressResponder` warnings on sampled routes. A Next development timing error was also observed during rapid route changes. Neither was reproduced on the fresh production setup page. Follow up on the pressable semantics and retain a focused keyboard/screen-reader review; do not treat a functioning screenshot as accessibility proof.
