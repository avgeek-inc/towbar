## Architecture decisions

1. Keep `packages/towbar-core` as the manifest/operation contract owner, `towbar-api` as the authorization/admission/service owner, `towbar-worker` as durable orchestration, and `towbar-deployer` as the remote runtime executor. UI, REST and MCP invoke shared service operations rather than separate implementations.
2. Add named, workspace-owned Integrations with immutable IDs and stable human-readable slugs, provider-specific validated configuration, capability metadata, encrypted credentials, revision and connection health. Store a manifest reference as a slug and resolve it to an ID/revision during admission. Scope grants limit repository, environment, purpose and external-secret namespace. Binding a reference must never grant a repository writer integration-management authority.
3. Keep identity-provider policy under Team Settings, using the same credential envelopes but separate administrative permissions. Never expose credentials through generic integration inspection or MCP.
4. Introduce an explicit discriminated app deployment object: `deployment.type` is `dockerfile`, `static`, `image`, `railpack`, `nixpacks`, `buildpacks`, or `compose`. Common runtime fields remain shared; type-specific fields must reject unsupported combinations. Compose references, overrides, builder files and build contexts resolve from the same immutable revision. Migrate unreleased examples/fixtures and internal normalized DTOs together; do not silently interpret incompatible fields.
5. Resolve build placement in this order: app override, environment default, repository default, runtime server. Explicit placement resolves only to a registered authorized server with verified SSH identity and prepared build capability. Explicit failure never falls back unless declared. Architecture and transfer strategy are validated before admission.
6. Manifest-owned sections cover `rollout`, `storage`, `backups`, `secretSources`, `observability`, and `ingress`. Integration credentials and identity enforcement are never stored in Git. Environment object merge/array replacement rules remain explicit; identity and provider type changes require validation rather than cross-union merging.
7. Admit an immutable operation plan with integration IDs/revisions, source commit, runtime/build server IDs, image digests, secret version references and declared capabilities. Persist no secret plaintext. Revalidate queued actor authority and active integration grants at effect time; stale or revoked inputs fail closed.
8. Extend the server coordinator with build, runtime, volume/database maintenance and patch/reboot reservations. Establish lock order before adding workflows. External effects must be discoverable by ownership labels/idempotency keys; uncertain responses trigger reconciliation, not blind retries.
9. Eligible stateless workloads default to health-gated start-first replacement. Stateful single-writer volumes, databases, singleton jobs, fixed host ports and incompatible Compose services require an explicit recreate/maintenance policy. Application rollback cannot reverse database migrations.
10. New provider/plugin/runtime versions must be pinned and reviewed in a dependency matrix. Prefer existing official cloud SDKs, Docker Compose tooling, pack and OpenTelemetry Collector. Do not implement OTLP wire formats or Compose interpolation manually.

Update the parity and evidence ledger before moving the slice to complete.

## Verification strategy

- CI provisions its own pinned PostgreSQL and Temporal test services. Dedicated required test invocations reject missing or skipped test output. Missing Docker or infrastructure is a failure, never a successful skip.
- Split required jobs into API/auth/database, Docker/protocol, app lifecycle, resource/recovery lifecycle and forwarding/scanner lifecycle groups. Upload summaries/logs even on failure. Production image build and fresh-stack smoke remain independent gates.
- Test-only ownership labels, random local ports, per-run database names and cleanup prevent disruption of existing development infrastructure.
- Keep original source revisions and all authorization inputs in integration tests; never weaken production permission checks to repair a harness.
- Protocol/emulator tests are not live-cloud proof. Record exact external prerequisites and acceptance procedures. Container package checks are not VM reboot proof. Go cross-compilation is not architecture execution proof.
- Use a supported disposable VM runner for patch/reboot gates and architecture-specific runtime validation. Do not create paid/live infrastructure or change real IdP policies merely to make a checkbox green.
- Re-run current tree gates after cross-cutting schema/service changes. Rerun affected lifecycle tests after each slice; full regression and production images at milestone boundaries.
