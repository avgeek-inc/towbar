# Towbar v2.0.0 release readiness

Verified on 21 September 2026 from `release/v2.0.0`. The branch contains all commits from `origin/main` and is a fresh-install release: Towbar 1.x databases and manifests are intentionally not supported.

## Decision

The branch is ready for pull-request review. All local release gates pass, including the six isolated integration groups, production Compose startup and recovery, and HIGH/CRITICAL scans of the exact API, worker, and web images. The active `main` ruleset now requires the aggregate **Required CI** check with strict branch freshness. Create the release tag only after that check passes on the pull request.

Live provider accounts, public DNS/TLS, physical passkeys, inbox delivery, and a fresh supported VM remain release-operator acceptance checks. The local fixture and protocol emulators do not claim to prove those external systems.

The ordinary package test run permits optional real-Docker skips; release acceptance comes from the isolated Docker group above, which ran all 216 deployer tests with zero skips.

The CI harness also starts from a genuinely empty runner: the API group builds its own isolated SSH/Docker target image, and production image scans keep Trivy's advisory cache in a disposable Docker volume outside the retained evidence directory. This prevents an existing developer image or root-owned scanner cache from changing the gate result.

Dockerfile and static builds reuse cached layers only when the stored cache marker matches the requested immutable commit. A changed revision forces an uncached build before the marker is advanced, preventing equal-size files with equal archive timestamps from producing a stale image.

## Documentation and UI audit

The release screenshot manifest contains 28 canonical routes with light and dark captures, for 56 JPEGs total. `pnpm docs:check` verifies file existence, unique names, canonical routes, both themes, JPEG dimensions, and guide references. The screenshot runner now validates its notification-provider fixture before capture and rejects 404 pages, runtime overlays, and failed-query views.

The final UI audit covered current navigation, integrations, repository manifests, apps/resources, server preparation, terminal, monitoring, personal settings, team settings, and table controls. The review fixed the shared popover trigger, removed redundant controlled modal/drawer roots that emitted React Aria press warnings, normalized table text spacing and compact controls, and moved provider catalogue metadata out of the route component.

The modularity review also checked the largest source files and every explicit complexity/max-lines exception. Large remaining modules are cohesive protocol or transaction boundaries: the manifest parser, database schema, deployer phase coordinator, remote shell primitives, and fixture route harness. Splitting them during release hardening would separate shared invariants without reducing product risk. The fixture harness already delegates team, repository, Scout, monitoring, event-history, log-drain, and terminal state to focused modules.

## Release-operator acceptance

Before tagging the release:

1. Confirm the pull request's branch-protected aggregate **Required CI** check passes against the current `main` revision.
2. Exercise disposable GitHub and GitLab accounts: grant, webhook, repository discovery, preview, status/comment, disconnect, and reconnect.
3. Exercise each advertised cloud/backup provider with disposable least-privilege credentials and restore known data.
4. Prepare a fresh supported Ubuntu host, deploy an app and managed resource, confirm public TLS/Cloudflare behavior, then test rollback and removal.
5. Verify invitation, password reset, email change, and notification delivery in representative mail/vendor clients.
6. Verify authenticator, recovery-code, and physical passkey flows in supported browsers.
7. Confirm the published image architecture matrix and scan every image digest that will be attached to the release.

These checks involve systems outside the local test harness. A failure blocks the release tag even though the branch is locally ready for review.
