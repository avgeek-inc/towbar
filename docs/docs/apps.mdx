An Application is a service declared in a connected GitHub or GitLab repository. Towbar builds a committed source revision or runs a prebuilt OCI image, then manages its release on a registered server. A Compose workload groups multiple repository-owned services into one deployment.

Towbar keeps the desired configuration in Git. The dashboard shows the effective manifest, secret status, deployment history, logs, and current state; it does not create a second workload definition.

One manifest `id` identifies the app across renames and file moves. A Repository sync imports that declaration for each mapped environment, but leaves the currently running release alone. A deployment then builds or resolves an image and promotes it on the environment's server after its checks pass. The app can reach a Resource on the same private Docker network; its connection credentials live in Towbar secrets rather than Git. A Preview is a separate, temporary instance for an eligible pull request.

## Define an app

Create one file under `.towbar/apps` and give it a stable `id`. This minimal Dockerfile app listens on port 3000 in production:

```yaml title=".towbar/apps/web.app.yml"
id: web
name: Web
deployment:
  type: dockerfile
  context: .
  dockerfile: Dockerfile
container:
  port: 3000
health:
  path: /health
environments:
  production:
    server: 192.0.2.10
```

Declare `production` in `towbar.yml`, map it to a branch, and register the example server IP before syncing. See the [Application manifest](/docs/apps/manifest) for every top-level field and the rules for environment overrides.

## Configure runtime

[Container and health](/docs/apps/configuration) covers process ports, capacity, private networks, persistent volumes, and readiness. [Routing and TLS](/docs/apps/routing) covers domains and certificates. Declare secret names in the manifest and save their values in [Secrets](/docs/secrets).

### Choose a health endpoint

Use an unauthenticated HTTP path that can respond when the app is ready. Set its startup allowance and review how readiness gates promotion in [Container and health](/docs/apps/configuration).

### Supply configuration

Declare build and runtime secret names in the manifest, then save their values in Towbar. [Secrets](/docs/secrets) explains the separate stages, value references, and preview isolation.

## Pick a deployment mode

Use an existing [Dockerfile](/docs/apps/modes/dockerfile), build a [static site](/docs/apps/modes/static), run a [prebuilt image](/docs/apps/modes/image), or choose [Railpack](/docs/apps/modes/railpack), [Nixpacks](/docs/apps/modes/nixpacks), or [Cloud Native Buildpacks](/docs/apps/modes/buildpack). A multi-service project uses [Compose](/docs/apps/modes/compose). [Deployment modes](/docs/platform-deployments) compares them and explains build servers and rollout strategies.

## Deploy and verify

Open the app and choose **Deploy**. Follow the stages until the attempt reaches a final result, then verify the service response. Start with a manual deployment; enable [automatic deployment and previews](/docs/apps/automation) after the basic path works. [Deployments and releases](/docs/deployments) explains image promotion and rollback.

## Scheduled jobs

Declare recurring commands in the app manifest and deploy that configuration before a job can run. [Scheduled jobs](/docs/apps/jobs) covers cron, runtime access, output, overlap, manual runs, and pause behavior.
