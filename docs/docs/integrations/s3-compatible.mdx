---
title: "S3-compatible storage"
description: "Configure an S3-compatible endpoint for managed database backups and restores."
---

Use the `s3` integration for an S3-compatible object store other than AWS S3 or Cloudflare R2. Create a bucket and credentials scoped to the intended objects, versions, and prefix. The endpoint must be reachable from the Towbar installation; keep credentials in the root-owned control-plane YAML file.

```yaml title="/etc/towbar/towbar.yml"
integrations:
  s3:
    enabled: true
    endpoint: https://objects.example.com
    region: us-east-1
    bucket: towbar-backups
    prefix: production
    addressingStyle: auto
    allowPrivateNetwork: false
    accessKeyId: "<access-key-id>"
    secretAccessKey: "<secret-access-key>"
```

Set `addressingStyle` to `auto`, `path`, or `virtual` as required by the service. Enable private-network access only for an intentionally internal endpoint. A private CA can be supplied as Base64 through `customCaBase64` when using a custom endpoint. Run `sudo towbar config validate`, then `sudo towbar restart`. The provider appears under **Manage → Integrations → Backup providers** when the local shape is valid.

Configure a managed resource's [backup policy](/docs/backups), create a real backup, and complete a [fresh-target restore](/docs/restores). Check remote object permissions, versioning, retention, and the final restore state before relying on it for recovery. A configured chip alone does not prove the endpoint accepts writes or reads. Rotate keys by applying new YAML, verifying an operation, and then revoking the old keys. [Cloudflare R2](/docs/integrations/r2) has its own integration slug and setup guide.
