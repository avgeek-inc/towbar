Towbar records provider-neutral events and sends each matching event to its subscribed destinations. Credentials live in `/etc/towbar/towbar.yml`. Email recipients, Slack channels, and Telegram chats are managed in **Manage → Notifications**. Discord webhook pairs and webhook push endpoints live in YAML; their event subscriptions are selected in the dashboard. The provider list remains visible even when a runtime connection is missing.

| Provider     | What you configure                                | Setup guide                                              |
| ------------ | ------------------------------------------------- | -------------------------------------------------------- |
| Email        | SMTP connection and recipient addresses           | [Email (SMTP)](/docs/integrations/notifications/email)   |
| Slack        | Bot token and channel IDs                         | [Slack](/docs/integrations/notifications/slack)          |
| Discord      | Webhook ID and token pairs                        | [Discord](/docs/integrations/notifications/discord)      |
| Telegram     | Bot token, chat IDs, and optional topics          | [Telegram](/docs/integrations/notifications/telegram)    |
| Webhook push | HTTPS URLs, optional headers, and signing secrets | [Webhook push](/docs/integrations/notifications/webhook) |

## Decide who receives an event

Workspace destinations receive matching events from all apps and resources. An app or resource manifest can add read-only Email, Slack, Discord, or Telegram destinations for that entity; see [manifest notification routing](/docs/deployment-manifest#route-notifications-for-one-app-or-resource). Webhook push remains workspace-only.

Each destination can subscribe to **Deployments**, **Backup & Restore**, and **Alerts & Incidents**. Preview events follow Deployments; service health and Scout incidents follow Alerts & Incidents. New runtime-managed Discord and webhook destinations start with no subscriptions, so select at least one category before expecting routine events.

## Apply runtime changes

Set `notifications.enabled: true` and add the relevant provider under `notifications.providers`. Run `sudo towbar config validate` and `sudo towbar restart`. Invalid YAML, duplicate IDs, missing credentials, or unsafe destinations fail validation. The [runtime configuration reference](/docs/self-hosting/environment-variables#notifications) lists the common shape; each provider guide has a focused example.

## Delivery history

Open **Manage → Notifications → Health → Deliveries** to filter persisted attempts by provider, category, or entity. The list includes workspace and manifest destinations. Inspect an attempt's status, timestamps, safe provider error, and retries before changing a route. A succeeded delivery means the provider accepted it; it does not prove a recipient read it.

Towbar resolves credentials when a delivery runs, retries transient failures with bounded backoff, and keeps history after a destination is removed. Authentication failures call for correcting YAML and restarting; a wrong subscription calls for changing the destination's category in the dashboard. Repeated rate limits pause the affected destination rather than blocking the underlying app or resource operation.
