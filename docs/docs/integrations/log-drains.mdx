---
title: "Log forwarding"
description: "Configure reliable server log drains in Towbar's YAML configuration."
---

Towbar supports New Relic, Axiom, Better Stack, Datadog, OpenTelemetry OTLP, and Grafana Loki. All six providers appear under **Manage → Log forwarding**. A provider without runtime credentials shows a configuration empty state.

Set `logForwarding.<provider>.enabled` and its native `config` map. For example:

```yaml title="/etc/towbar/towbar.yml"
logForwarding:
  otlp:
    enabled: true
    config:
      endpoint: https://collector.example.com
      auth: bearer
      username: ""
      apiKey: replace-me
      headers: []
      caCertificate: ""
```

The configuration document is never stored in PostgreSQL or returned to the UI. Towbar derives a SHA-256 revision from it and reconciles that revision to prepared servers. PostgreSQL retains only provider-neutral applied state, health, bounded diagnostics, backoff state, and incident history.

Application logs are collected independently of deployment workflows. The forwarder uses bounded batching, memory and disk queues, retry windows, and resource limits so a slow provider cannot block an app. Authentication failures stop retries and mark the provider accordingly. Repeated HTTP 429 responses use exponential backoff; after the third rate-limit response the destination is marked rate-limited and deferred for 24 hours. Towbar emits one configured service-health notification when either terminal condition is reached.

In each app or resource manifest, `logDrains` selects the runtime-configured providers that receive its container logs. For example, `logDrains: [betterstack, otlp]` forwards to both. Environment overrides replace the list, so `logDrains: []` disables forwarding in one environment. The runtime holds the provider destination and credentials; the workload does not need to repeat either one.

Use `logDrainAttributes` for non-sensitive, provider-specific context:

```yaml title=".towbar/apps/web.app.yml"
logDrains: [betterstack, otlp]
logDrainAttributes:
  betterstack:
    team: storefront
    tier: critical
  otlp:
    team: storefront
```

Each provider's attribute names must use lowercase letters, numbers, and underscores. Values are plain text, up to 256 characters, and up to 16 attributes are allowed per provider. Attributes cannot replace Towbar's standard fields. Towbar adds the service name, app ID, deployment ID, environment, repository ID, server ID, and workspace ID to forwarded records. OTLP exports custom attributes as resource attributes.

Resources use the same selection and context fields:

```yaml title=".towbar/resources/cache.resource.yml"
id: cache
name: Cache
type: redis
server: 192.0.2.10
logDrains: [axiom]
logDrainAttributes:
  axiom:
    team: storefront
```

Environment overrides replace the whole `logDrainAttributes` map. When a base
manifest has provider context, clear both fields to disable forwarding in one
environment:

```yaml title=".towbar/apps/web.app.yml"
environments:
  staging:
    logDrains: []
    logDrainAttributes: {}
```

The provider page shows non-secret runtime settings, server delivery status, and accepted and dropped **batch** counts from the latest server check. A batch may contain many log events, and these counters are shared by workloads using that provider on a server. The app and resource **Log forwarding** page shows the providers selected by that workload's manifest and the same server-level delivery evidence. Generate workload traffic and confirm receipt in the destination when validating a new configuration; an applied state or accepted batch does not prove the provider retained every event.
