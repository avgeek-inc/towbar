Towbar reads deployment configuration from the Git revision being deployed. The dashboard validates and operates that declaration without maintaining a second workload configuration.

## Choose a mode

| Mode         | Use it for                                                           | Guide                                        |
| ------------ | -------------------------------------------------------------------- | -------------------------------------------- |
| `dockerfile` | An existing Dockerfile, including builds that need protected secrets | [Dockerfile](/docs/apps/modes/dockerfile)    |
| `static`     | Generated browser assets served from a runtime image                 | [Static site](/docs/apps/modes/static)       |
| `image`      | An image built elsewhere                                             | [Prebuilt OCI image](/docs/apps/modes/image) |
| `railpack`   | Source detection for a new project                                   | [Railpack](/docs/apps/modes/railpack)        |
| `nixpacks`   | An existing Nixpacks project                                         | [Nixpacks](/docs/apps/modes/nixpacks)        |
| `buildpack`  | Cloud Native Buildpacks                                              | [Buildpacks](/docs/apps/modes/buildpack)     |
| Compose      | A multi-service project                                              | [Compose](/docs/apps/modes/compose)          |

Each guide includes a complete, validated entity example from `examples/platform-modes`. Builder images accepted by the manifest must be pinned to immutable digests. Choose the mode first, then configure shared [container and health](/docs/apps/configuration) fields.

## Configure a source build

Set the context and builder-specific options in `deployment`. [Dockerfile](/docs/apps/modes/dockerfile), [static site](/docs/apps/modes/static), [Railpack](/docs/apps/modes/railpack), [Nixpacks](/docs/apps/modes/nixpacks), and [Buildpacks](/docs/apps/modes/buildpack) each have a complete example. Dockerfile and static builds can receive protected build values; Railpack, Nixpacks, and Buildpacks reject build secrets. Cancellation removes staged source and unpromoted images.

Build caches belong to a workload unless you configure an authorized shared `cache.scope`. Inactive cache scopes are reclaimed after 30 days, so keep the build reproducible after a cold cache.

## Prebuilt images

Use `deployment.type: image` with an explicit non-`latest` tag or digest. Towbar resolves a tag to an immutable digest before execution and fails if the digest changes. For private images, reference an enabled [OCI registry integration](/docs/integrations/oci-registry). See the [prebuilt image guide](/docs/apps/modes/image) for a complete manifest.

## Build servers

Set `buildServer` in `towbar.yml` to use one prepared server for every app in an
environment. `direct` streams the verified image archive to the runtime server:

```yaml title="towbar.yml" highlight={2-5}
version: 2
buildServer:
  ip: 192.0.2.20
  transfer: direct
  allowRuntimeFallback: false
environments:
  production: {}
```

An environment or app can override the default. Use `null` when one app should
build on its runtime server:

```yaml title=".towbar/apps/worker.app.yml" highlight={3}
id: worker
name: Worker
buildServer: null
deployment:
  type: dockerfile
  context: apps/worker
  dockerfile: apps/worker/Dockerfile
container:
  port: 3000
environments:
  production:
    server: 192.0.2.10
```

For registry transfer, set `transfer: registry` and add the enabled registry
integration name. The build server must belong to the team, have trusted SSH
credentials, be prepared, and support the requested architecture. Without
`allowRuntimeFallback: true`, an unavailable build server fails closed.

Compose projects always build on their runtime server because Compose resolves
the service graph as one project.

## Rolling and recreate strategies

Stateless apps default to health-gated rolling replacement. Configure only the
limits that differ from the defaults:

```yaml title=".towbar/apps/api.app.yml" highlight={3-8}
id: api
name: API
rollout:
  type: rolling
  replicas: 2
  maxSurge: 1
  maxUnavailable: 0
  minimumHealthySeconds: 15
container:
  port: 3000
environments:
  production:
    server: 192.0.2.10
```

Use `recreate` for a single-writer volume, fixed host port, or another workload
that cannot run two releases together:

```yaml title=".towbar/apps/files.app.yml" highlight={3-6}
id: files
name: Files
rollout:
  type: recreate
  maintenanceMode: true
  reason: The app uses a single-writer volume
container:
  port: 3000
environments:
  production:
    server: 192.0.2.10
```

Rolling admission checks capacity before replacement and promotes only after
the candidate stays healthy. App rollback selects an earlier image; it does not
reverse a database migration or restore persistent data.

## Compose projects

Compose entities live under `.towbar/compose` and point to repository-owned Compose files. Towbar validates the resolved project and builds on its runtime server. Replacement uses `recreate` or `maintenance`, not rolling promotion. The [Compose guide](/docs/apps/modes/compose) includes a full service example and the admission restrictions.

## Reference an integration

Manifest fields use the stable runtime names shown on the Integrations pages. For example, `registry: registry` selects the configured OCI registry. Repository sync and queued execution verify that the provider is enabled and supports the requested capability.
