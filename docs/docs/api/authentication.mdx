## Keys and permissions

Create keys in **Manage → API & MCP**. Each key belongs to its creator and workspace. The key inventory shows its name, prefix, permissions, last use, expiry, and revocation status. Each user manages their own keys. Every key works with both the API and MCP.

| Setting     | Options                                                                                        |
| ----------- | ---------------------------------------------------------------------------------------------- |
| Permissions | Read only or full access                                                                       |
| Expiry      | 30 days, 90 days, 1 year, or never in the UI; an explicit future ISO timestamp through the API |

Read-only keys can call `GET` routes and the corresponding MCP tools. They cannot change profile data, deploy, sync, create keys, manage credentials, or trigger checks. Full-access keys can invoke mutations allowed by the creator's current role. Owner-only actions remain owner-only, including server management, secret changes, AWS credentials, and automatic deployment controls.

Towbar checks the current user and workspace membership on every request. Disabling the user, removing membership, expiring a key, or revoking it prevents subsequent requests. Role changes apply immediately to new requests. A request already accepted may complete, and accepted background jobs continue independently of the key. Revoking a key does not cancel a deployment.

## How authentication works

Send the key in an HTTP header:

```http
Authorization: Bearer twb_YOUR_KEY
```

Towbar generates keys from 32 cryptographically random bytes and stores only a SHA-256 hash and short identifying prefix. The raw secret appears once in the creation response. Key lists never return hashes or complete secrets. The token is not a JWT and does not contain credentials or workspace details.

API and MCP do not accept browser cookies as authentication. Browser sessions continue using cookie authentication and origin validation. Requests with an `Origin` header must match the configured control-plane origin; CLI and server clients normally omit it. Use HTTPS outside local development. Never put keys in URLs, logs, screenshots, or committed configuration.

## Create and rotate programmatically

A full-access API key can create another key through `POST /settings/api-keys`. Permissions still use the same user and workspace. Read-only keys cannot create keys. Rotation creates an independent key: revoke the old key after updating your clients.

```bash
curl -X POST 'https://YOUR_API_HOST/v1/api/settings/api-keys' \
  -H "Authorization: Bearer $TOWBAR_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"name":"CI deployments","access":"write","expiresAt":null}'
```

The `201` response contains `{ "key": { ...metadata }, "token": "twb_..." }`. Store `token` immediately. Revoke with `DELETE /settings/api-keys/{keyId}`. Revocation is permanent; create a replacement if needed. No key is created during installation—sign in once to bootstrap your first key.

## Configure rate limits

Set these in the API process environment or your self-hosted `.env` file and restart the API service:

```dotenv
TOWBAR_API_RATE_LIMIT_MAX=60
TOWBAR_API_RATE_LIMIT_WINDOW_SECONDS=60
TOWBAR_TRUSTED_PROXY_HOPS=0
```

| Variable                               | Default | Allowed range     |
| -------------------------------------- | ------- | ----------------- |
| `TOWBAR_API_RATE_LIMIT_MAX`            | `60`    | 1–100000 requests |
| `TOWBAR_API_RATE_LIMIT_WINDOW_SECONDS` | `60`    | 1–86400 seconds   |
| `TOWBAR_TRUSTED_PROXY_HOPS`            | `0`     | 0–8 hops          |

The fixed window starts at the first request after expiry. All API and MCP keys from the same client IP share that window. Changing keys or alternating interfaces does not create a new allowance. The browser control plane and GitHub webhook have their own authentication behavior and are not part of this bucket.

With zero trusted proxy hops, Towbar uses the socket address and ignores `X-Forwarded-For`. Behind a reverse proxy, set the exact number of controlled proxy hops and prevent direct access to the API listener. An incorrect count can group every client under the proxy IP or trust a spoofed address. For example, one directly connected Caddy proxy typically requires `1`; an additional CDN changes the topology and needs a matching configuration.

The counter is updated atomically in PostgreSQL. A database outage fails requests rather than bypassing the limit. REST event streams count once when connected; subsequent reconnects count as new requests.
