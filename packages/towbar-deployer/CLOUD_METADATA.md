# Cloud provider metadata audit

Reviewed 6 September 2026. Scope: automatically identify a managed server and its instance type without asking for a cloud account credential. These are best-effort observations, not attested identities or authorization signals. Provider responses were verified against the documentation below and exercised with protocol fixtures; no live instances of the new providers were available for validation.

## Supported contracts

| Provider          | Endpoint / protocol                                                                            | Result                                                                                      | Evidence                                                                                                     |
| ----------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| AWS               | IMDSv2 token, then `/latest/meta-data/instance-type`                                           | Exact instance type; no IMDSv1 fallback                                                     | [AWS IMDSv2](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configuring-instance-metadata-service.html) |
| Google Cloud      | `/computeMetadata/v1/instance/machine-type`, `Metadata-Flavor: Google`                         | Machine type extracted from its resource path                                               | [GCP metadata keys](https://cloud.google.com/compute/docs/metadata/predefined-metadata-keys)                 |
| Azure             | `/metadata/instance/compute/vmSize?api-version=2021-02-01&format=text`, `Metadata: true`       | VM size                                                                                     | [Azure IMDS](https://learn.microsoft.com/azure/virtual-machines/instance-metadata-service)                   |
| Oracle Cloud      | `/opc/v2/instance/shape`, `Authorization: Bearer Oracle`                                       | Shape, including flexible shapes; observed CPU and memory remain authoritative for capacity | [OCI metadata](https://docs.oracle.com/en-us/iaas/Content/Compute/Tasks/gettingmetadata.htm)                 |
| Hetzner Cloud     | `/hetzner/v1/metadata/instance-id`                                                             | Provider only; numeric ID is validated then discarded                                       | [Hetzner metadata](https://docs.hetzner.cloud/reference/cloud#server-metadata)                               |
| DigitalOcean      | `/metadata/v1/id`                                                                              | Provider only; numeric ID is validated then discarded                                       | [Droplet metadata](https://docs.digitalocean.com/products/droplets/how-to/access-metadata/)                  |
| Akamai / Linode   | PUT `/v1/token`, then JSON `/v1/instance` with `Metadata-Token`                                | Instance type; discard other instance properties                                            | [Metadata service API](https://techdocs.akamai.com/cloud-computing/docs/metadata-service-api)                |
| Alibaba Cloud ECS | Security-hardening token, then `/latest/meta-data/instance/instance-type` at `100.100.100.200` | ECS type; no unauthenticated fallback                                                       | [ECS metadata](https://www.alibabacloud.com/help/en/ecs/user-guide/view-instance-metadata/)                  |

All other supported endpoints use `169.254.169.254`. Metadata tokens are short-lived, host-local protocol tokens, not account API keys. Hetzner and DigitalOcean do not document an exact plan in these metadata services. Their logos appear beside observed CPU/RAM, without deriving a plan from capacity. Exact plans could be added later through opt-in, read-only cloud API integrations.

## Reliability and privacy decisions

- Eight fixed probes run concurrently with a 2.5-second overall deadline, within the existing five-second SSH command timeout. Each HTTP operation has a 750 ms timeout. Daemon workers prevent a hung or trickling response from keeping the process alive after the deadline.
- Proxy environment variables are bypassed; redirects are refused. No discovered URL is followed. Only the two fixed metadata addresses above are contacted.
- Scalar reads are capped at 1 KiB. Linode instance properties are capped at 16 KiB because they are a JSON object. No user-data, SSH key, certificate, or account-credential endpoint is requested. Only provider and validated type leave the script.
- Unknown, oversized, malformed, or conflicting responses fail closed to hardware-only display. Provider availability never fails server preparation or checking.
- Existing saved checks remain readable. Provider-only records use a nullable type; no database migration is needed.
- Probes run during server checks, not on every Scout sample. No new credentials, agent service, packages, or ongoing cloud API polling are introduced.

## Validation

Protocol fixtures execute the actual Python script and assert endpoint addresses, required headers, token exchanges, response size limits, normalization, ambiguous identities, and the overall deadline. Core tests cover persisted records and provider-only fallback. Browser checks cover exact-type and provider-only displays in the Servers list and Connection card, including small logos in both themes.
